# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Services Directory Toolkit is a Chrome extension (Manifest V3, Chromium browsers only) that adds diagnostic and query tools to the HTML pages served by ArcGIS Server REST endpoints (`.../rest/services/...`). It packages the bookmarklets from [ESRI REST Diagnostics](https://github.com/raykendo/ESRI_REST_Diagnostics) into one tool. The code is plain vanilla JS with no framework, no bundler, and no runtime dependencies.

It is an independent continuation of Ken Doman's [Map Services Enhanced](https://github.com/raykendo/Map-Services-Enhanced), which stopped at 1.4.0 on Manifest V2. The `upstream` remote points at the original, and its full history is in this repo. The old name should appear only where it credits the original: the README, the manifest and `package.json` descriptions, and the options page footer. Keep Ken's line in `LICENSE`, which the build adds to the zip. Work before the first store release follows `docs/superpowers/specs/2026-10-09-store-readiness-design.md`.

## Working to the spec

Section 4 of the spec is the definition of done for every phase. A change in behaviour starts with a failing test, and `README.md`, `CONTRIBUTING.md`, this file and `.coderabbit.yaml` must match the code when the phase ends. Each pull request lists the IDs it closes from the spec's findings register (Appendix A), and how it resolved each one. CodeRabbit reads this file as its code guidelines (`knowledge_base` in `.coderabbit.yaml`) when it reviews a pull request.

`docs/superpowers/plans/` holds the implementation plan for each piece of work. `docs/design/` holds the UI design review for issue #7, with its mockups and screenshot scripts, and the spec records the decisions it settled. The bug report form (`.github/ISSUE_TEMPLATE/bug_report.yml`) links to the README's `#compatibility` anchor, so keep that heading's name.

## Commands

Requires Node 22.13 or a later 22.x, or Node 24 or later (`engines` is `^22.13.0 || >=24`, and `.nvmrc` pins 24). Run `npm install` first, and `npx playwright install --no-shell chromium` once for the browser tests.

- `npm run lint`: ESLint 10 (flat config in `eslint.config.js`) over the repo, with warnings treated as errors. Formatting rules come from `@stylistic` (2-space indent, double quotes, semicolons). Code under `src/` may not write HTML strings (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`). Content and popup scripts must be one bare block, content scripts must add listeners, timers and `chrome.*` callbacks through `SDT.guard`, may not call `chrome.storage.*.set`, `remove` or `clear`, and read settings only through `SDT.settings`, code outside `src/src/lib/` may not pass a defaults object to `chrome.storage.*.get`, and lib files may not declare top-level names (see [Architecture](#architecture)).
- `npm test`: `npm run test:unit` (`node --test` over `tests/unit/`), then `npm run test:e2e` (Playwright, in `tests/e2e/`). See [Browser tests](#browser-tests). Unit tests for `src/src/lib/` load the lib files into a `vm` context with a stub `chrome` (`tests/unit/helpers/sdt.js`); compare values made there with `plain()`, because they have that context's prototypes.
- One unit test file: `node --test tests/unit/build.test.js`. One browser spec, or one test in it by title: `npx playwright test tests/e2e/pages.spec.js -g "options page"`. `--grep @cdp` picks the tests tagged `@cdp`.
- `npm run build`: lint, then zip into `build/<package name>-<version>.zip`. Only files the extension references ship (see `scripts/lib/extension-files.js`), including those the service worker loads with `importScripts`, plus the root `LICENSE`. The build fails on a missing or unreferenced file, a `chrome.runtime.getURL` or `importScripts` call without string literals, a `web_accessible_resources` key, a version mismatch between `package.json` and `src/manifest.json`, or a content-script group, extension page or service worker that loads a script using an `SDT` namespace before the lib file that defines it. To test the zip the way CI does, run `node scripts/build.js` (the build without lint), unzip the zip into an empty folder, and run Playwright with `EXT_PATH` set to that folder.
- `npm run test:live`: checks that each feature appears (presence only, no values) on Esri's public sample server (override with `SDT_TEST_SERVER`) in the installed Google Chrome, headless unless `HEADED=1`. It isn't part of CI. Branded Chrome ignores `--load-extension`, so `tests/live/smoke.js` loads the extension over CDP (`Extensions.loadUnpacked`), which needs `--enable-unsafe-extension-debugging`, Developer mode in the throwaway profile, and `ignoreDefaultArgs: ["--disable-extensions"]`.
- `node scripts/probe-tokens.js`: probes how a server handles tokens, for the token work (settings in the comment at the top of the file). Run it by hand on servers you can sign in to, signing in by hand with `PROBE_MANUAL_LOGIN=1` on federated or SSO servers. It isn't part of CI, and git ignores its output in `probe-output/`.
- To try the extension by hand, open `chrome://extensions`, turn on Developer mode, and use "Load unpacked" on `src/`.

## Browser tests

Each test starts Chromium, headless unless `HEADED=1`, with the extension from `src/` (or `EXT_PATH`). Playwright's default headless shell can't load extensions, so the fixtures in `tests/e2e/fixtures.js` use `channel: "chromium"`; `CHROME_PATH` runs the suite in another Chromium build through `executablePath`.

`tests/fixtures/fake-arcgis.js` answers requests to three origins: `https://arcgis.test`, an Enterprise-style server that signs users in with an `agstoken` cookie or a token and hides secured services from anonymous listings, and two ArcGIS Online stand-ins, `https://services9.arcgis.com` and `https://www.arcgis.com`. The `signIn` fixture sets the server's sign-in cookie, and `openPopupTab` takes a Page to report its real tab id. `seedStorage(items, area)` and `readStorage(keys, area)` write and read `chrome.storage.sync`, or `chrome.storage.local` when `area` is `"local"`. The browser resolves no host names, and Playwright doesn't route a redirect's target, so following a redirect fails the test: browser tests can't open a secured page anonymously, and the unit tests cover its 302. The fixtures come from two files. `catalog.js` holds the services, layers and the rows that counts are computed from, and `pages.js` renders HTML shaped like the 10.9 and 11.x Services Directory. They include an asynchronous GP task with a `submitJob` form (`Transport/RouteTools`), a FeatureServer `queryDomains` page, and `/docs/rest/services/overview`, a page outside ArcGIS Server whose path holds `/rest/services`. Catalog keys that start with `_` are fixture data the fake server never sends. `whereMatcher` lists the where clauses it can evaluate. A test can replace a response with `fakeServer.override(pattern, handler)`, and the handler may answer late or never. `fakeServer.requests` records only the method and URL. To check where a token or `f=json` went, use `fakeServer.calls`, which keeps each request's `origin`, `path`, `query` and form `body` apart. `tests/e2e/requests.spec.js` covers the request budget and the token rules. `tests/unit/url-patterns.test.js` and `tests/e2e/url-patterns.spec.js` are the URL-pattern matrix. `tests/e2e/axe.js`'s `axeViolations(page, { include })` runs axe-core with the WCAG 2.2 AA tags in the light and dark colour schemes; on host pages, pass `include` to scope it to the extension's elements. The harness's manifest check turns on Developer mode and reloads the extension, because Chrome reports unrecognised manifest keys only then, and never unknown keys inside `action`. All of this data is synthetic. Don't commit responses captured from Esri's servers: their terms don't allow redistribution.

A request to one of those origins that has no fixture gets a 404 and fails the test. A test also fails on a request to another host, a request the fake server can't interpret (such as a where clause it doesn't support, or an override that returns no status), an override that never matched a request, a dialog, and any console error or uncaught exception. A test can allow a console error through `expectedErrors`, and clears the other violations with `harness.forgive()` after asserting that the right list caught them. The checks have two limits. Playwright doesn't route the network requests of the real toolbar popup, because it has no Page, so popup logic is tested through `openPopupTab`. And errors during service worker startup, or during the popup's initial load, happen before the error hooks are in and go unseen.

The main CI job runs the suite against the unzipped build, with `EXT_PATH=dist`. The non-blocking Chrome 120 job runs it against `src/` and skips the `@cdp` tests, because Chrome 120's DevTools protocol has no `Extensions.triggerAction`. Chrome 120 is the manifest's `minimum_chrome_version`, which `tests/unit/manifest.test.js` pins. Chrome for Testing 120 crashes at startup on macOS 27, so the suite can't run on it locally there. `CONTRIBUTING.md` describes the manual Chrome 120 check before a release.

`tests/e2e/known-bugs.spec.js` holds bugs from the findings register that reproduce today, as `knownBug()` cases that Playwright expects to fail. The change that fixes one turns its `knownBug()` into `test()`, unless the comment above the case says otherwise. `SHOW_KNOWN_BUGS=1` runs them as normal tests. Use it after renaming classes or changing the requests the extension sends, to check that each case still fails on its last assertion and not in its setup. Find elements by role or text where possible, because class names change during the store-readiness work.

## Layout

The extension root is `src/`, which holds `manifest.json` and `icons`. The scripts sit one level deeper, in `src/src/`. Paths in the manifest and in `chrome.runtime.getURL(...)` resolve relative to `src/`. For example, the manifest's `src/inject/inject.js` is **`src/src/inject/inject.js`**. `importScripts` paths resolve against the service worker's own file, so `background.js` loads `../lib/sender.js`.

## Architecture

**Content scripts** (`src/src/inject/`) do nearly all the work. The manifest injects them by URL pattern:
- `inject.js`, `status.js`, `mapImages.js` (and `inject.css`) run on `/rest/services`, with or without an instance path before it, a query string after it, or anything below it:
  - `inject.js` is the main tool. It fetches service JSON, collects metadata, feature counts, and field/domain counts, and color-codes spatial references.
  - `status.js` shows the status indicator, a 24 px ring in the bottom-right corner that spins while any `sdt-loading-*` class is on `<body>`, with a visually hidden `role="status"` line that says "SD Toolkit: loading" and then "SD Toolkit: finished loading", at most once a second. It takes no clicks and has no listeners. It also enables the toolbar button. Settings are on the options page, which the popup's Options link opens.
  - `mapImages.js` shows map image previews when you hover over links.
- `queryTest.js` runs on `.../query` operations, with or without a query string, and handles the query builder, SQL helpers, and the "Select All" behavior.
- `printTask.js` runs on GP `execute` and `submitJob` pages, in Esri's casing, and pre-fills the default `Web_Map_as_JSON`.

Each script is wrapped in a bare `{ ... }` block, which lint enforces for content and popup scripts. This is deliberate: all of an extension's content scripts in a frame share one isolated world, even across `content_scripts` groups, and the blocks keep their `const` declarations from colliding. Shared code lives in `src/src/lib/` (spec section 5). Each lib file is a classic script that adds one namespace to `globalThis.SDT` and declares nothing at the top level, so running it twice is harmless. Every `content_scripts` group lists the lib files first, in one order, and `page_action.html` loads them first too; the build fails if a script uses an `SDT` namespace before the file that defines it. The namespaces, in load order: `SDT.dom` (`loadElement`, `text` and `clear`), `SDT.guard` (the extension-context guard), `SDT.auth` (`scopeOf`, the token scope, and `pageToken`), `SDT.url` (`build` and `stripForFilter`), `SDT.net` (`fetchJson` and the request limiter), `SDT.page` (`classify`) and `SDT.settings` (the settings schema, `validate`, `parse` and `read`). The Phase 2 plan's "Public API" section lists every member. `src/src/lib/sender.js` (`SDT.sender`, the service worker's sender check) is in no content-script group: the service worker loads it with `importScripts`, and the build checks that load order too. `src/src/lib/writer.js` (`SDT.writer`, which saves settings) is in no content-script group either: only the options page loads it, because content scripts never write to storage. `SDT.guard.whenActive` runs a function now, or once a prerendered page is shown.

Every request goes through `SDT.net.fetchJson`, which resolves to `{data}` or `{error}` and never rejects. If an update cuts the script off while a request is out, it never settles, so code after the `await` doesn't run. Lint bans `fetch` and `XMLHttpRequest` in content and popup scripts, and `tests/unit/no-legacy-requests.test.js` checks that no `ajax` copy or IE-only branch is left. Automatic requests, the ones sent without a user action, also go through `SDT.net.pageLimiter()`, one per isolated world, which enforces spec section 4.3: at most 50 per page view and 4 at once, only inside the page's scope, cancelled on `pagehide`, and stopped for the page by an HTTP 429 or 503. A row it leaves out shows "Not loaded: request limit reached (50)", or "Not loaded: the server answered HTTP 503, so automatic requests stopped" with the status it got, until Phase 5's Load more and status bar. Clicks in the Query and Find Helpers and map previews on hover are user actions and skip the limiter.

A `token` in the page URL goes only to URLs in the page's scope, in a form POST body, with `redirect: "manual"`. The scope is the origin plus the path before the first whole-segment `/rest/services`, compared in lower case except an ArcGIS Online org ID. Paths under `admin`, `tokens` or `manager`, and instance paths that still hold `%2f`, `%2e`, `%25` or `%5c` after parsing, have no scope and get no token. Requests without a token stay GETs, with no headers of their own. `SDT.url.build` drops any `token` already in a URL, in any case. Link filters in `inject.js` and `mapImages.js` test each href without `token`, `f` and its fragment, skip links outside the page's scope, and skip links to the page itself (its `?f=pjson` link). Map previews never send the token.

Every content script first calls `SDT.page.classify(location, document)`, which reads only `location.pathname` and `document.contentType`, and confirms the page with any one of three markers (a `.breadcrumbs` element, the title cell's text, or a Services Directory heading), because 12.1's classes are unverified. On a JSON view (`application/json` or `text/plain`) or a page that isn't a Services Directory page, the scripts do nothing, so the toolbar button stays disabled there too. `queryTest.js` runs only on `query` pages and `printTask.js` only on `gpTask` pages. Every class the extension injects starts with `sdt-`.

The content-script patterns match the path and the query string together, and are case-sensitive, so they follow Esri's casing. They also match pages that aren't Services Directory pages, such as `/docs/rest/services/overview` or `/page?x=/rest/services`, which the classifier turns away. A Query Helper pattern ends in `/query` or `/query?*`, so `queryDomains` and `query/` don't get it, and the GP patterns name `GPServer/*/execute` and `GPServer/*/submitJob`.

After an extension update, Chrome cuts off the old content scripts: `chrome.runtime.id` reads undefined and `chrome.*` calls throw. So a content script's top level only declares names and ends with one `SDT.guard.onLoad(...)` or `SDT.guard.run(...)` call, and every listener, timer, `chrome.*` callback and XHR callback goes through `SDT.guard.listen` or `SDT.guard.wrap`. Lint enforces this for listeners, timers and inline `chrome.*` callbacks under `src/src/inject/`, and `tests/unit/guard-entry-points.test.js` runs each group with the context gone. `SDT.settings.read`, like `SDT.net.fetchJson`, never settles in a cut-off script.

**Page action popup** (`src/src/page_action/`): `search.js` searches the REST endpoint tree of the active tab, and `url_shortener.js` strips unneeded query parameters. `options_link.js` makes the Options link at the foot of the popup open the options page with `chrome.runtime.openOptionsPage()`. The search and the shortener read the active tab's URL with `chrome.tabs.query`, which works only because clicking the toolbar button grants `activeTab`. The content-script `matches` give extension pages cross-origin access to every host (Chrome ignores their paths for this), but they don't expose `tab.url`. Keep `activeTab`: the activeTab test in `tests/e2e/action-popup.spec.js` fails without it. The search sends the tab URL's token to the tab's scope, in POST bodies. The activeTab test replaces the real popup's `fetch` with one that goes through a routed extension page, because Playwright doesn't route the popup's own requests.

**Background** (`src/src/bg/background.js`) is a classic service worker that loads `src/src/lib/sender.js` with `importScripts`. The toolbar button starts disabled (`action.default_state: "disabled"`, with `chrome.action.disable()` on install and browser start as a fallback). `status.js` sends an `enableAction` message on Services Directory pages, through `SDT.guard.whenActive` (so a prerendered page sends it once shown) and again after a back/forward cache restore, but not on JSON views or other pages the patterns match. The service worker acts on it only when `SDT.sender.accepts(sender, chrome.runtime.id)`: this extension, a tab, its top frame and `documentLifecycle` `"active"`. It then enables the button for that tab, and logs a failed `enable()` with `console.debug`. Chrome clears per-tab action state on navigation, so the content-script `matches` in the manifest are the only URL rules. Don't reintroduce a `declarativeContent` `ShowAction` rule: in Chrome 154 it did not re-enable an action disabled with `chrome.action.disable()`. `inject.js`, `mapImages.js` and `queryTest.js` start from `SDT.guard.onLoad` (MV2 used a `sendMessage` handshake).

**Settings** are defined once, in `SDT.settings.schema` (`src/src/lib/settings.js`): each entry's key, type, default, allowed values or range, label and storage area. The keys are `autoMetadata`, `autoFeatureCounts`, `showMapImages`, `mapImageWidth` and `mapImageHeight` (whole numbers from 50 to 2000), `queryHelperSelectAll` (`get`, `post` or `donothing`), `defaultWhereClause`, and `defaultWebMapAsJSON` (empty, or a JSON object of at most 100 KB). The web map lives in `chrome.storage.local` and starts empty; the rest are in `chrome.storage.sync`.
- **Reading.** `SDT.settings.read(keys)` resolves to validated values: a missing or invalid stored value reads as its default, and a stored `nothing`, from the in-page form that Phase 3 removed, reads as `donothing`. Content scripts read settings only this way and never write them (lint enforces both), and code outside `src/src/lib/` may not pass a defaults object to `chrome.storage.*.get`.
- **The options page** (`src/src/options/`) is static HTML with one control per schema key, whose `name` is the key. `tests/unit/options-page.test.js` checks each control's type, values, range, label and error line against the schema. `options.js` checks each field with `SDT.settings.parse`, shows errors under the fields with `aria-invalid`, and saves with `SDT.writer.save`.
- **Saving** (`src/src/lib/writer.js`). A key is written when its new value differs from what is stored and the user changed it on the page or the stored value is invalid, so a change made in another window survives. Sync items are checked against Chrome's per-item and total quotas first. `storage.local` is written before `storage.sync`, and put back if the sync write fails. The page says "Saved" only after both writes succeed.
- Field and coded-value counts have no setting: `inject.js` runs them on every layer page, on two constants, until Phase 5's Count values button (#45). Changes apply when a page is reloaded (SET-11); open tabs don't update.

Code under `src/` builds DOM with `SDT.dom.loadElement` and text nodes, never HTML strings. Lint enforces this.
