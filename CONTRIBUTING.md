# Contributing

Requires Node 22 (22.13 or later) or Node 24 or later, and `.nvmrc` pins 24. Run `npm install`, then `npx playwright install --no-shell chromium` once for the browser tests.

- `npm run lint` checks the code with ESLint, then checks the colour tokens in `src/src/lib/sdt.css` against WCAG 2.2 AA contrast (`npm run contrast` prints the full table). Warnings fail.
- `npm test` runs the unit tests, then the browser tests. The browser tests load the extension into headless Chromium against a fake ArcGIS Server, so they need no network. Set `HEADED=1` to watch them.
- UI the extension adds gets an axe-core check through `tests/e2e/axe.js`, in the light and dark colour schemes, scoped to the extension's own elements on host pages, where `hostPage: true` runs the dark pass on a dark host page, and a keyboard-only test.
- Shared code goes in `src/src/lib/`, as classic scripts that add to the `SDT` namespace. Add a new lib file to every `content_scripts` group and to `page_action.html`, after the files it uses. Shared styles go in `src/src/lib/sdt.css`: use its `--sdt-*` tokens, and scope every selector to an `sdt` class (`tests/unit/sdt-css.test.js` checks). Build icons with `SDT.icon(name)`. Unit tests load the lib in Node through `vm` (see `tests/unit/helpers/sdt.js`). Content scripts start, and add listeners, timers and `chrome.*` callbacks, through `SDT.guard`, so they stop quietly after an extension update. Lint checks this. Requests go through `SDT.net.fetchJson` (lint bans `fetch` and `XMLHttpRequest` in the scripts), and automatic ones also through `SDT.net.pageLimiter()`. `inject.js` reports its progress through `SDT.status.job(kind, total)` and sends its requests with the job's `fetch`; lint exempts member calls to `fetch` on an identifier named `job`, so that name is reserved for those jobs. Lint also rejects HTML entity literals such as `&amp;` in strings under `src/`, because the extension sets text and not markup (TOOL-7). The status bar's browser tests are in `tests/e2e/status-bar.spec.js`; `bulkRoot(count)` in `tests/e2e/fixtures.js` makes a services root with that many services, and `toolkitStarted(page)` waits for the extension to start on a page. The service worker loads the lib files it needs with `importScripts` (today only `src/src/lib/sender.js`); the build counts them and checks their order. Settings are defined once, in `SDT.settings.schema` (`src/src/lib/settings.js`). To add one, add a schema entry and one control on the options page whose `name` is its key; `tests/unit/options-page.test.js` checks that they match. Content scripts read settings with `await SDT.settings.read(keys)`, which validates them, and never write them: lint rejects `chrome.storage.*.set`, `remove`, `clear` and `get` under `src/src/inject/`, and a defaults object passed to `chrome.storage.*.get` anywhere outside `src/src/lib/`. The options page saves through `SDT.writer` (`src/src/lib/writer.js`), which no content-script group loads.
- `npm run build` runs the linter, then packages the files the extension uses into `build/services-directory-toolkit-<version>.zip`. The versions in `package.json` and `src/manifest.json` must match.
- `npm run test:live` checks that each feature appears (it doesn't check values) on Esri's public sample server, in your installed Google Chrome. Set `SDT_TEST_SERVER` to test a different server.

CI also runs the browser tests on Chrome for Testing 120 as a non-blocking check. Chrome for Testing 120 crashes at startup on macOS 27, so it can't be run locally there. Before a release, check the minimum Chrome version by hand: install Chrome for Testing 120 (`npx @puppeteer/browsers install chrome@120 --path ~/chrome-for-testing`), load `src/` unpacked, and try the services root, a layer page, a query page and the popup. Also open a 12.1 root, layer and execute page (Esri's `utility.arcgisonline.com` runs 12.1) and check in DevTools that `td.breadcrumbs`, `td.titlecell` and the `<b>Fields: </b>` list are still there. The store-readiness spec's Phase 2 section records why.
